## TL;DR
- Speaker A demoed their personal "LLM wiki". It runs daily routines that pull data from Teams/email, the GitHub org, and untracked local files. Speaker C demoed WorkOS, a shared GitHub repo of skills and context for a team. It is already piloted with the client Payworks.
- The main open issue is how personal and team context should fit together. The options were one shared space with git policies, or separate personal and team spaces joined by an explicit sharing channel. Nobody has solved this yet.
- Speaker A said WorkOS is "very, very complex" and would need to be about 10x simpler to sell. Several design gaps are still open: where artifacts are stored, scheduling and auto-pull, conflict handling, structured data, and how easy it is to install.

## Key points
- **Speaker A's personal wiki routines:**
  - Daily wiki ingestion from every available connector (Teams, email), sorted into entities and tagged external, internal or personal.
  - Daily GitHub org digest (172 repos, 41 PRs), which updates priorities, index and log files.
  - Daily local-changes ingestion of files git doesn't track (e.g., the Oracle workshop prep).
  - A daily priorities routine.
- **Scaling to a team (Speaker C):**
  - Several people would process the same messages. At best that duplicates work; at worst the results conflict.
  - Sensitivity: should the system ingest everything, or only what a person explicitly drops into an inbox?
- **Speaker A's answer:** the tags would allow a "safe to share" skill that exports tagged content. The difference is that the LLM wiki solves a personal problem and WorkOS solves a team problem.
- **Skills:** these go beyond maintenance. They should include role-specific skills like a presales deck, a demo, or an architecture analysis, roughly 20 across roles. Some stay personal and some are shared with the team.
- **Packaging (Speaker B):** the personal setup works as a standalone package. Team WorkOS could be an add-on, but it needs much more hands-on work with the client (the Payworks experience). Roll out one use case at a time.
- **Why WorkOS (Speaker C):**
  - The team loses context from meetings people weren't in.
  - Everyone redoes the same work (e.g., presales decks, Oracle pack packaging).
  - Shared context plus reusable skills should speed things up a lot.
  - Plan: an internal project this quarter to roll WorkOS out in R&D, test it in real use, then take it to clients.
- **WorkOS architecture (Speaker C's demo):**
  - A GitHub repo containing skills (mostly for product roles), business context (company, competitors, templates, recent insights) and an OS harness (skills, agents, team memory).
  - Paths that aren't gated auto-commit, push and merge to main through an end-of-turn hook, controlled by an `autosync` config setting.
  - Gated files (skills, general context, OKRs) go to a branch and need a PR. A web UI lets people approve or reject those PRs; the local server didn't start during the demo.
  - Decisions from transcripts are logged automatically, and new context is cross-linked to initiatives, projects and features.
- **Answers to Speaker A's questions:**
  - Only text artifacts live in the repo. Payworks asked for final PRD PDFs to go to Confluence, which was handled as a one-off.
  - A setup skill onboards the client and asks about MCP connectors.
  - There is no scheduler at Payworks. GitHub Actions for wiki linting and consistency checks were planned but not built.
  - There is no auto-pull.
  - Conflicts haven't been simulated. The argument is that transactional folders like meetings are append-only, and the files people can actually clash on are gated.
- **Setting approval per directory:** the admin sets it through branch policies (Azure for Payworks, GitHub internally). End users just talk to the agent and never see this.
- **Linking personal context:** not built. Speaker A proposed an "add personal" skill: it asks which folders to use and what to sync, then creates a routine. Speaker C pointed out that each person's routines differ, so they would need local runs or cloud runs.
- **Speaker A's challenge: why not SharePoint, Confluence or Notion plus skills that pull and push?**
  - Speaker C's answer is a hybrid. Context the agent generates and keeps using (stakeholder maps, decisions on the Oracle engagement) belongs in the repo as MD files.
  - Reusable human artifacts (PPT sales decks, PDFs) belong in OneDrive.
- **Speaker B's framing:** there are 3 types of context (the engine/settings, personal, and team) × several storage systems. The goal is to keep that matrix small.
- **Structured data:** Speaker C thinks hundreds of initiatives may need a table or database. Speaker A isn't convinced: their wiki has about 10k files and works fine.
- **Large files:**
  - Speaker A suggested storing build scripts instead of binaries. Speaker C said final PDFs with human input still have to be stored.
  - Speaker A then suggested an output index MD that lists every generated file and where it lives, so the agent doesn't regenerate it. Speaker C agreed.
- **Sync:**
  - Speaker A suggested a pull routine set up during onboarding (daily or every 4 hours). Speaker C uses GitHub Desktop to auto-sync every 30 seconds and says users should never have to think about it.
  - People use different tools (Claude Code, Cursor, Devin) with different scheduling. Hooks would fire too often.
  - Speaker A wants the install to be minimal, with the setup skill installing prerequisites like the git CLI.

## Open questions / follow-ups
- Personal vs team model: everything shared with git policies, or separate spaces with an explicit sharing channel?
- How to handle overlapping ingestion when several people process the same emails or transcripts. What's allowed to be ingested automatically, and should it be opt-in only?
- Where artifacts live (repo vs OneDrive/SharePoint/Confluence/Notion) and the wiki-summary + link pattern.
- Whether and when structured data (initiatives, projects) needs a database or spreadsheet instead of MD files.
- Scheduling and auto-pull across tools (Claude Code, Cursor, Devin), and GitHub Actions vs local vs cloud routines.
- Conflict handling: nobody has simulated two people ingesting the same transcript.
- Linking personal context: design the "add personal" skill and its sync routine.
- Simplify the product about 10x before selling. Present it as chat and keep the UI out of pitches, though Speaker C says the UI is still needed for onboarding.
- Minimal install for non-developers (no Python or git CLI assumed).
