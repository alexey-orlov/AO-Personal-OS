- Speaker B (likely SoftServe account or presales, inferred) interviewed the SoftServe engineers on the Maximo account: Lukáš (A), Tomasz (C) and Oleksii (D). The goal was to understand delivery pain points and where AI agents could help, ahead of a proposal to the customer.

## Key points
- **Documentation and knowledge:**
  - Information has been kept on tracking boards and lost with each tool switch (Jira → Miro → Aha).
  - A GitHub wiki repo exists, but nobody updates it, and reviews take about a month.
  - Legacy data and external components are undocumented, and some components have a bus factor of 1.
- **Versioning and deployment:**
  - 2–3 production streams run on different machines with different feature sets, with no proper versioning.
  - The deployment process changes month to month.
  - Building an image for testing can take about 2 hours of cherry-picking branches across submodules.
  - There are 100+ repos. Some are submodules and some have no release or staging branches.
  - The team is now trying a monthly staging branch as a release, which is in its first month.
  - Picking the right base branch for a feature often takes longer than building the feature.
- **Org structure:**
  - Maximo (written "Maxima" in the transcript) is a spin-off of AES.
  - SoftServe works mostly through Richard and Diego (product managers/owners), and things then go up to Maximo's C-level.
  - Maximo has its own small dev team: robotics and vision hires plus one generalist engineer.
  - Hardware and PLC work is done by a third party, Carnegie Robotics.
  - SoftServe builds the requested features, proposes ideas (which Maximo has to approve), and does remote debugging and production support.
  - SoftServe engineers cover vision, AI, robotics and autonomy, and often swap roles.
- **Stack:**
  - About 99% is Python and C++ ROS2 apps on Ubuntu.
  - The simulation stack runs in Omniverse / Isaac Sim, which Lisa is working on.
  - Small amounts of PLC ladder logic and KRL code for the KUKA arm.
- **Testing:**
  - The short loop is iterating in simulation.
  - Testing on real hardware needs a spare machine, an operator and the right setup. Lukáš has been waiting since Monday to test one change.
  - Build and deploy through GitHub Actions takes 20–25 minutes, and feedback comes from the on-site operator.
  - Robots spend most of their time on production sites, often remote desert locations with a single Starlink link.
  - There used to be a rule of 4 days production and 1 day testing per robot per week.
- **Root cause of remote limits:**
  - The team is in Europe and the robots are in the US, and the team no longer travels to site.
  - SSH access and logs are fine: logs stream in real time to AWS and are viewable per service in Grafana.
  - What's missing is ground truth and a way to observe physical behavior remotely: pick/place accuracy, driving accuracy, position and speed, and subjective things like arm motion looking "unsafe".
  - Vision misdetections and software crashes can be debugged remotely, but you need to know where to look, for example images stored on the machine.
- **Hardware specs:**
  - The third party's docs only cover static values (motor power, max velocity, steering angle).
  - Dynamic behavior isn't documented: acceleration, steering rate, slipping on sand or grass.
  - SoftServe estimated those values from collected sensor logs using basic data science and scripts.
  - The vendor knows no more about the system's behavior than SoftServe does.
- **AI usage:**
  - Lukáš finds manual log review faster because he knows the system.
  - The system is highly coupled: one component can talk to 11 others, each of which talks to 5–6 more.
  - Agents miss changes on one side of a dependency.
  - Without documentation, the agent reads the whole codebase and burns tokens.
- **Sim-to-real gap (Tomasz):**
  - Low-level and hardware components aren't simulated faithfully, so features that pass in simulation fail on the robot.
  - The vision pipeline refactor (moving the camera view from top-down to horizontal by changing the arm pose) has been sim-only for 3 months because production takes priority.
  - Tomasz suggests having a KUKA arm with end-of-arm tooling in the Wrocław or Lviv lab, since pick/place is about 70% of the robot's job. Tomasz and Wojtek think the client probably wouldn't fund it.
- **Maximo engineers:** they likely face the same "know where to look" problems, but they visit the production sites and Carnegie Robotics more often. They sometimes help SoftServe with testing on site.
