**OneView and how it ships (Pulak)**
- A platform team (App Core) and 4 domain verticals, each paired with business analysts from the product team; about 100 code repos; microservices deployed single-tenant on AWS (each client in its own account, with one or more isolated environments running all of OneView), so clients can sit on different versions and configurations.
- Quarterly releases: about 2 months of development, then about 1 month after code freeze of testing and bug fixing, a named improvement area. After the freeze a few people test (automated where tests exist, manual otherwise), developers fix what is found and add docs and tests, then move on to the next release as bandwidth allows. Release testing runs on representative data and configurations; some of it is left to the last minute, and they want to shift it left.
- UI test automation started last month: too few tests yet, no coverage metric. The tests they have were written with AI; they backfill tests in sprints during the code-freeze window.
- **Where time goes (Pulak's read; not measured):** requirement and design iterations across time zones, between the BAs and the teams (inferred): clarifying one change "can take a week". Writing code is the fast part; PR reviews take longer, with "massive back and forth", because AI generates a lot and things slip unless every line is read. That was seen with plain Copilot, without deep grounding.
- Systems: Confluence for requirement intake, published documents and cross-team coordination, not for daily development; all Numerix work in Jira, every code change mapped to an item, under an initiative → epic hierarchy ("Epic Therapy" as transcribed, inferred); code in GitHub, whose default automated code review is on and catches a lot but isn't connected to their instructions or knowledge base (Enoch: so it sees only the repository). Process and Jira statuses are standardized within OneView; other Numerix teams ("RiverX" as transcribed, inferred) differ by product, team make-up and geography. AI-generated story points are not tracked.

**Their AI-DLC toolkit (Pulak's demo)**
- Teams took AWS's AI-DLC training at different times and in different variations, and the AWS repo changed "drastically" within four months; they kept the parts that fit, "walking before we can run". Pulak had sent a pre-read on the team set-up, Jira and Confluence use and this toolkit, which SoftServe had read.
- One repo in two parts: a **knowledge base** on OneView (the ~100 repos, runbooks, troubleshooting guides, guides per persona: support, presales and professional services as internal users, developers and BAs as builders), incomplete but growing and kept up to date; and an **AI toolkit** of 6 agents mapped to a growing set of skills, with evals per agent that are not yet run for every test.
- The flow, each step a skill backed by the knowledge base, templates and rules: a one-line prompt or Jira item → triage (new or existing) → requirements on their template and checklists, as partners to the BAs → optional reverse engineering of existing code → design and design review → task breakdown with test scenarios → ready to build. It knows which team owns which repo, so it splits a feature into Jira items per team and for the UI. **Automatic Jira creation is deliberately off** (no write access) until the outputs are trusted. Developers then self-review locally against the code-review guidelines before raising a PR. Not done yet: more GitHub review automation, and docs and release notes updated after a feature; the wiring to update the knowledge base after work or reverse engineering is in place.
- The base package compiles into Kiro-, Claude- and GitHub-Copilot-compatible packages: clone the repo and the agents appear in the Kiro and Copilot agent menus; steering files ("steering cards" as transcribed, inferred) are to pick the agent automatically; the install step is to be simplified.
