## Key points
- **Format/goal**: SoftServe wants to learn AI Lakehouse capabilities, positioning, and roadmap to build a repeatable packaged offer, not a bespoke solution. Conversational, not a sales pitch; Gero explicitly invited candour on roadmap and blunt feedback. Session recorded for SoftServe's reference.
- **Naming**: Autonomous Data Warehouse → Autonomous (AI) Lakehouse is a rebrand only; nothing functionally changed. "26ai" is the *version* (vs 19c), not a separate product — 26ai carries vector capabilities needed for agents.
- **Managed service**: Oracle handles backups, patching, upgrades; granular CPU scaling (no T-shirt sizes); workload-based auto-configuration (e.g. hybrid columnar compression on by default for Lakehouse, off for transaction processing).
- **Differentiators claimed**: Exadata hardware advantage vs Databricks/Snowflake standard hardware; converged architecture avoiding multi-engine sprawl (Mongo/Neo4j/Elastic/Snowflake); translytical — transactions + analytics in one DB, important because agents need real-time, not historical, data.
- **Gold-layer play**: Typical pattern is ADP/Databricks/Spark for bronze+silver, Autonomous as the gold layer. Cited customer pain with Databricks gold layer: slow queries, concurrency limits for BI users/agents, cost multiplication, and a catalog that went down frequently.
- **Security**: SQL firewall, virtual private database (row-level policies, e.g. country-scoped), dynamic data redaction/masking (e.g. last 4 digits of an account) — enforced consistently across DB, Iceberg, and AI capabilities. Taras flagged relevance to a SoftServe NHS opportunity where masking was a hard requirement.
- **Graph**: Knowledge-graph traversal on the same relational data via a metadata layer — no duplication or ETL to Neo4j. Example: real-time circular-transaction fraud detection.
- **Iceberg / ADP integration**: ADP currently works with Delta only; Autonomous works with Iceberg only. Today's options: (a) recommended — move/copy data to the gold layer via Spark JDBC into Autonomous; (b) a PM workaround using Uniform metadata plus manual catalog integration. Native catalog integration expected once ADP supports Iceberg ("soon"). Gero noted full AIDP–Lakehouse integration is a question nobody at Oracle has a clean answer to yet.
- **"Live AI Hub" quick win**: Autonomous as a connectivity hub via database links to Postgres, SQL Server, BigQuery, IBM, legacy Oracle; build a semantic layer and apply AI in ~2 days without building a lakehouse from scratch. Data Studio GUI (ELT drag-and-drop, hundreds of connectors, Table AI Assistant, analytical views) to be rebuilt this summer as catalog-centric with embedded AI assistants.
- **Go-to-market discussion** (Gero + Javier): wave 1 = AI on Oracle data sitting in third-party clouds; wave 2 = extend to non-Oracle data/object stores in those clouds. Consensus that the further from the Oracle estate, the harder the case — customers consolidated on Databricks usually need to feel gold-layer pain first.
- **Cost/multi-cloud** (Pawel's question): Autonomous appears as a native service inside AWS/Azure/GCP regions (Exadata in the partner data centre), so the host cloud's ingress/egress policy applies; within OCI there is no inter-service network traffic charge. Javier could not confirm cross-tenancy/FastConnect cost specifics. Architecturally, a single Autonomous instance can serve as one point to query data across clouds and on-prem.
- **References**: few public case studies so far, but several internal ones (Exadata 19c + Databricks-on-Azure customer using Autonomous as the glue; a gaming company using bronze/silver in Spark with gold-layer departmental isolation). Oracle open to sharing anonymised architectures on request.
- **Not covered (time)**: Iceberg catalog roadmap, analytical views/semantic layer, Select AI + Select AI agent with agent memory (claimed ~10x token savings), ontology creation, Iceberg performance, "Ask Oracle" prebuilt agents.
