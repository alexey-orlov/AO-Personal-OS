## Key points
- **What's in WorkOS (Alexey's walkthrough):**
  - **Context library:**
    - Strategic context: business info, segmentation, competitors, stakeholders.
    - Templates for the documents WorkOS produces: product briefs/PRDs, micro-job specs, prototypes.
    - Ongoing context, such as user insights, which the agent writes.
    - Output artifacts.
    - Index pages: initiatives and the product map, which link documents to features across many-to-many relationships.
  - **OS harness:** skills, sub-agents, team memory, governance/consistency files, the console and the WorkOS docs.
- **How often each part changes (Sapan):**
  - Day-to-day work, including outputs: high.
  - Skills: medium.
  - Strategic context: medium. Alexey corrected this from "low", since it's updated per product, quarterly or monthly.
  - Agents, orchestration and index pages: low.
- **Principles Alexey stated:**
  - Agents work much better reading files than calling APIs.
  - Each piece of data has one master system.
  - Agents rely on a specific file structure and on links/tags that humans shouldn't edit by hand.
  - The same document can look different in Confluence than the version the agent uses.
- **Four candidate workflows:**
  1. Repo only, synced to the team via Git.
  2. One-way publishing from the repo to Confluence through the MCP integration. Intended for final PRDs, prototypes, and possibly the segmentation matrix.
  3. External sources pulled in only when needed, e.g. a code repo or a feature-specific dashboard.
  4. Two-way editing in both places. Alexey argued against it.
- **Seamless user experience (Lila's question):**
  - The Azure CLI plus DevOps extension is needed so users never have to deal with PRs directly.
  - Edits to non-gated files sync in the background.
  - Gated files, such as business info, are submitted for approval by typing a chat command.
- **Performance cost of external calls (Michael):**
  - Alexey said the cost is acceptable for narrow, direct lookups.
  - Shared overview knowledge should live as files.
  - Michael took this as meaning "we're not blocked". He raised the longer-term question of the company's strategy for indexing, RAG or knowledge graphs.
- **Sapan's three goals:**
  - Keep Confluence as the knowledge base; don't rebuild it in Azure.
  - Align with organizational policy (Lila, Josh and Mo).
  - Keep processes consistent across teams, e.g. product and engineering.
- **Confluence's role (Sapan):**
  - Product context means human-readable documents: PDF/DOCX/XLS/HTML prototypes.
  - Confluence already has established access, versioning and audit controls, and engineering already goes there to find hand-off documents.
- **Claude Code as the only tool:** Lila noted that the setup commits PMs to Claude Code rather than Claude chat. That's a heavier, more technical environment for less technical users.
- **Internal debrief (vendor side only):**
  - Frustration that client requirements keep shifting. Sapan joined mid-engagement, and security concerns came up late.
  - Roberto noted that Confluence was earlier agreed to be out of the MVP with Marlene/Selena. Sapan's marketplace and Confluence asks are new.
  - Alexey's concern: 20-step technical write-ups could look overwhelming and push the client toward a "simpler" process. He'd prefer a visual or demo.
