# D — Context inventory for shippable Oracle packaging skills

_Research pass, 2026-09-17. READ-ONLY inventory — nothing was edited in either repo or in OneDrive._

Scope: what context must travel with a set of Claude Code skills that produce the five packaging artifacts — **feature list · sales deck · sales one-pager · interactive demo · mini-site listing** — so they do not degrade when run by someone else, on another machine, or in a cloud sandbox.

## The answer, up front

- **Ship ~14 items, ~450 KB.** The bundle is small because most of what the artifacts *depended on* was machine folklore, not knowledge. The load-bearing pieces are: the **41 KB `softserve-deck-base.pptx`** (without it a shipped deck skill cannot make a branded file at all), **`check-grammar.js`** (the only place Alex's rules exist as an executable test), the **`products[]` schema slice + visual-grammar §1–§5/§7**, the **design + client-document + research-standards rule sets**, the **demo playbook's 11 requirements**, one **reference demo**, a new **≤ 2-page engagement-context doc**, and a **versioned 91-row roadmap extract**.
- **Deliver as one standalone GitHub repo that is also a plugin marketplace**, internally split into `pack-docs` (feature list · one-pager · deck — python-pptx only) and `pack-web` (demo · listing — Node ≥ 22 + Chrome + the site repo). An in-repo plugin only loads when the session starts at that repo's root, and the packaging work happens in *other* trees, so a marketplace install is the only shape that puts the commands where the work is.
- **The three risks that actually bite:** brand fonts are licensed and absent off a managed Mac (gate on a computed fit report, never the eye); the customer-name / pricing deny-list exists today **only for the mini-site** and must be generalized to every artifact; and the pack ↔ use-case-map join is **free-text with drift and no id** on a map that churns weekly.
- **Two things to settle with Alex before building:** (1) the phrase **"13 shared components"** appears in no source — the closest match is a 9-layer solution-components grid plus 4 service/commercial rows, and a *different* per-pack feature anatomy is live in the Sept one-pagers; (2) the site commits to a **4–8-week PoV** (checker-enforced) while both pack one-pagers say **2 months** for S.

### F. Existing skills — `.claude/skills/` (22 skills, 3,115 lines total)

Read the frontmatter of all 22. Uniform convention: `name` (= folder name), `description` (long, trigger-phrase-rich, with NOT-for boundaries), `disable-model-invocation: false`, `user-invocable: true`. Eight carry a `references/` subfolder (`apple-notes-sync`, `book-finder`, `cv-tailor`, `draft-message`, `gym-log`, `message-writing`, `re-engagement-outreach`, `ss-monthly-report`).

- **None of the 22 would be called by a packaging skill.** They are all personal-workflow (calls, inbox, books, gym, CV, Apple Notes, Telegram, Clockify). `context-update` is the closest structural analogue but writes into Alex's personal wiki.
- **Conventions worth copying:** (1) `name:` must equal the directory name; (2) a description that is a *routing contract* — what it does, when to use it, and what it is NOT for; (3) the `references/` subfolder for anything the skill body would otherwise bloat with (the repo's own pattern: `message-writing/references/linkedin.md` etc.); (4) a self-check list at the end of the skill body, because `CLAUDE.md`'s learning loop says a rule not on a self-check list "is filed, not consulted"; (5) `ss-monthly-report`'s **abort-rather-than-guess** stance (unmappable prefix / total mismatch → stop) is the right stance for a packaging skill that hits an unmapped use case.
- **Anti-pattern to avoid:** `SoftServe-Work-OS/.claude/skills/CLAUDE.md` records that Claude Code scans **exactly one level deep** — a skill at `.claude/skills/{group}/{skill}/SKILL.md` is *silently* not discovered. Keep the packaging skills flat.

## 5. Delivery-model options

**The decisive constraint** comes from the plugin-migration proposal (`OneDrive/Microsoft Teams Chat Files/2026-09-15-skills-to-plugin-migration.md`, v3, §1): a folder under a project's `.claude/skills/` that carries `.claude-plugin/plugin.json` loads as a plugin **in place, with no install step** — but it "loads only when the session starts in the repo root (plain skills also load from subfolders; plugin folders do not)". The packaging work does **not** happen at the root of whatever repo holds the skills: the listing skill writes into the mini-site tree, the deck skill writes into a pack folder. So an in-repo plugin in a repo that is not the working repo is the wrong shape.

Second constraint: **the two audiences are not the same kind of user.** R&D (Vlad and team) run Claude Code, have Node and Chrome, and can install a plugin. SoftServe sales/presales largely do not run Claude Code at all — for them the deliverable is the artifact, not the skill.

| Option | Shape | Vlad / R&D laptops | Sales / presales | Cloud sessions | Updating | Verdict |
|---|---|---|---|---|---|---|
| **1. Standalone GitHub repo, published as a plugin marketplace** | `oracle-pack-skills` repo with `.claude-plugin/marketplace.json` at root + a plugin folder holding `skills/`, `assets/` (the 41 KB base, the reference demo), `references/` | **Best.** `claude plugin install …` once, then the commands resolve in *any* session — including one opened at the mini-site repo, which is where the work actually is. `${CLAUDE_PLUGIN_ROOT}` gives stable paths to the deck base and the schema. | Irrelevant to them; they consume outputs. | Works — a cloud session can clone the repo or install the marketplace. | `git pull` / plugin update; no version field needed (updates follow commits, per the proposal's Q2 reasoning) | **Recommended** |
| **2. A plugin folder inside `SoftServe-Work-OS`** | `.claude/skills/oracle-packs/` alongside the planned `os` plugin | Loads only at the Work-OS root — wrong working directory for pack work. Also couples a partner-facing Oracle asset to a repo that is being handed to Payworks; the Oracle packs are a different customer story. | — | Same root limitation | Rides the Work-OS release train, which is a pull request into **Payworks'** marketplace — wrong channel entirely | **No** |
| **3. Plain skills folder to copy** | `cp -r skills/* <target>/.claude/skills/` | Works immediately, no plugin mechanics, loads from subfolders too. But every copy diverges the moment someone edits one, and there is no update path. | — | Works | Manual, and silently stale | **Fallback only** — the right shape for a *pilot* with Vlad before investing in the marketplace |
| **4. Two units, not one** (a refinement of 1) | `pack-docs` (feature list · one-pager · deck) and `pack-web` (interactive demo · mini-site listing) as two plugins from one marketplace repo | `pack-docs` needs only python-pptx + the 41 KB base: a low enough bar that a presales engineer could run it. `pack-web` needs Node ≥ 22, Chrome and the site repo: R&D only. | `pack-docs` is plausibly installable by a technical presales person | Both | Same repo, one pull request | **Recommended as the internal structure of option 1** |

**Recommendation:** option 1 with option 4's internal split — one standalone GitHub repo that is both the marketplace and the home of the packaging plugin(s), with the pack **data** (roadmap extract, pack tracker snapshot, the engagement-context doc) versioned beside the skills. Two reasons beyond the table: (a) these skills are **data-hungry, not just prompt-hungry** — a plugin can carry the 41 KB deck base, the schema slice, `check-grammar.js` and a reference demo, which a "just copy the SKILL.md" approach cannot; (b) a separate repo keeps the Oracle packaging assets out of both Alex's personal OS and the Payworks-bound Work OS, which is the correct boundary for something Oracle and SoftServe sellers will see.

**Before committing, run the proposal's own step 0 spike** (30 min): the four facts it exists to settle — namespaced command form, `${CLAUDE_PLUGIN_ROOT}` resolution in a skills-directory plugin, agent scoped names, no leftover bare command — are marked "not on the docs pages we could reach" (§9). The fallback the proposal names is a top-level folder loaded with `claude --plugin-dir ./<folder>`.

**Keep the skills flat.** `SoftServe-Work-OS/.claude/skills/CLAUDE.md` records that Claude Code scans exactly one level deep, and a skill nested one folder deeper is *silently* not discovered — it disappears from autocomplete rather than erroring.
